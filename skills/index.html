SKILLS Y MCP

Saber hacer.
Poder hacer.

En el capítulo 14 viste a un agente ordenar los tickets de un viaje de trabajo. Pero en cualquier empresa hay reglas que el modelo no puede adivinar: qué se reembolsa, en qué apartado va cada gasto, a quién se envía. Y no solo de gastos: cómo se contesta a un cliente, cómo se piden las vacaciones, cómo se escribe un acta…

¿Cómo se lo cuentas todo sin llenarle la mesa de papeles que no necesita? El arnés no se lo enseña todo: le enseña un menú, y el modelo pide lo que le hace falta.

03 / EL MENÚ LO DECIDE
Lo que no se entiende, no se abre.
Al empezar, el modelo solo ve la etiqueta de cada skill: su nombre y una línea que la describe. Con eso decide si la abre. Elige cómo se presenta la política en el menú y mira qué suele pasar.




LO QUE VE EN EL MENÚ


LO QUE SUELE PASAR


Ilustración: lo que «piensa» el modelo y lo que hace son un guion escrito para mostrar la idea, no una medida.


Una etiqueta clara se usa. Una vaga es lotería. Si el nombre y la descripción dicen para qué sirve la skill, el modelo la reconoce al leer el encargo y la abre antes de empezar. Si no dicen nada, abrirla o no depende de que se le ocurra mirar.


¿Y si la pegamos siempre en las instrucciones? También funciona: estaría siempre en la mesa. Si la política es una página, cuesta casi lo mismo. El menú empieza a compensar cuando la empresa tiene decenas de manuales y cada tarea solo necesita uno.



04 / SABER Y PODER: MCP
Para hacer, hace falta una herramienta.
La skill es texto: le enseña a saber cómo hacer la nota. Pero enviarla a contabilidad o consultar el presupuesto es hacer algo fuera, y eso solo se consigue con una herramienta, como en el capítulo 12.
MCP es una forma estándar de ofrecer herramientas a un arnés. Alguien escribe un pequeño programa, un servidor MCP, que dice «tengo estas herramientas», y cualquier arnés que hable MCP lo puede conectar. Como un enchufe USB: cualquier ratón funciona en cualquier ordenador.

Las herramientas también van al archivador. Mira el tercer paso: al empezar, el modelo solo ve los nombres de las herramientas del servidor, y pide sus instrucciones justo antes de usarlas. Claude Code lo hace así cuando hay muchas herramientas: es el mismo truco que con las skills.


Saber sin poder, poder sin saber.




SOLO LA SKILL
Sabe, pero no puede
Hace la nota con las reglas de la casa, pero no puede consultar el presupuesto ni enviarla. Te la deja en un archivo para que la mandes tú.


SOLO EL SERVIDOR
Puede, pero no sabe
Consulta el presupuesto y puede enviar la nota, pero no conoce las reglas: enviaría a contabilidad una nota con propinas y sin la tasa aparte.


LAS DOS
Sabe y puede
Abre la política, hace la nota como la quiere contabilidad, comprueba el presupuesto y la envía.




Enviar no tiene vuelta atrás. En el ejemplo, el modelo ve que la nota se pasa del presupuesto y aun así la envía, y te avisa después. Un modelo no siempre para a preguntar. Que un agente pida permiso antes de algo irreversible lo decide el arnés: marca la casilla de arriba y vuelve a reproducir el ejemplo.



05 / EN LA VIDA REAL
Cómo son por dentro.


UNA SKILL PUEDE LLEVAR MÁS COSAS
Un cajón con varias carpetas dentro.
Además del SKILL.md, una skill puede guardar en su carpeta documentos de consulta, plantillas y pequeños programas. El modelo no los lee al abrir la skill: el SKILL.md le dice qué hay y cuándo usar cada cosa, y los abre solo si le hacen falta. Es el mismo truco del archivador, un nivel más adentro.
Los programas son especiales: el modelo no los lee, los ejecuta. Así una skill trae también sus propias herramientas. Sumar 40 tickets con un programa que ya está probado es más fiable que sumarlos de cabeza.
Ilustración: la política de Brújula de este capítulo es solo un SKILL.md. Los otros archivos son un ejemplo de lo que podría llevar.




UNA SKILL
Una carpeta con un archivo
Un archivo SKILL.md que empieza con la etiqueta, el nombre y la descripción que se ven en el menú. Debajo, las instrucciones, que solo se leen al abrirla.


UN SERVIDOR MCP
Un programa que ofrece herramientas
Se declara una vez en la configuración del arnés y sus herramientas aparecen junto a las demás. Puede consultar una base de datos, un programa de la empresa o una web. Uno sencillo, como el de contabilidad de este capítulo, cabe en unas pocas decenas de líneas.


CUÁNDO CADA UNA
Saber o poder
Si al modelo le falta saber cómo se hace algo en tu empresa, escribe una skill. Si le falta poder llegar a algo, como un servicio, unos datos o un botón, hace falta una herramienta, y MCP es la forma estándar de dársela.


CONSEJO 1
Nombre y descripción claros
Es lo único que ve el modelo para decidir. Di qué es y cuándo usarla, con las palabras que usaría alguien al pedir ese trabajo.


CONSEJO 2
Una skill, un trabajo
Mejor varias pequeñas que un manual gigante: así cada tarea abre solo lo que necesita.


CONSEJO 3
Lo irreversible, con permiso
Leer y consultar suele ser seguro. Enviar, pagar o borrar, mejor que el arnés te pregunte antes. El modelo no siempre parará solo.





PARA LLEVAR
Tres ideas.


1El modelo ve un menú, no los manuales.En la mesa solo va la etiqueta de cada skill. El manual entero se abre cuando hace falta.
2La etiqueta decide si se usa.Un nombre y una descripción claros hacen que la abra a tiempo. Una etiqueta vaga es lotería.
3Una skill enseña a saber. MCP deja hacer.Las herramientas se enchufan con un estándar, y lo irreversible debe pedir permiso.



LO QUE VIENE
Un menú, y abrir lo que hace falta.
Has visto el truco con las skills y con las herramientas: el modelo ve un índice corto y pide el resto cuando lo necesita. Un proyecto de verdad tiene cientos de documentos: lo que se pidió, lo que se decidió, los problemas ya resueltos. No caben en ninguna mesa. El mismo truco, aplicado a todo eso, se llama memoria, y es el siguiente paso.
